薪資計算系統　開發者手冊

這份文件的第一目的，是讓後來改這套系統的人（包括三個月後的你） 看得到 02 架構核心 那條規則。 這套系統過去每一個難查的 bug，都是違反它造成的。

單檔 HTML ≈ 10,700 行 無框架・無建置 IndexedDB + GitHub 同步

01　系統概覽

成衣代工廠的計件薪資系統。從接單、記工作量、算薪資，到對客戶請款。

技術棧

層用什麼備註
整體單一 HTML 檔無框架、無 npm、無建置步驟。用瀏覽器打開就是完整的 App
主資料IndexedDB pw9db單一 record，key main
照片IndexedDB pw9imgdb與主資料分離，避免 base64 撐爆主 record
UI 偏好localStorage主題、選單收合、工作量表的欄位開關與欄寬
雲端GitHub Contents API把整個 db 當 JSON 推到私有倉庫
登入PBKDF2-SHA256(600k) + AES-GCM可選的 key.enc 通關密語機制

設計原則

  1. 同一份資料只存一次。能推導出來的就不要存第二份——這是本系統最重要的原則，見 02
  2. 已發生的事凍結。主檔可以改，工單與工作量不行
  3. 鎖是算出來的，不是存出來的。結算鎖、請款狀態都用查的
  4. 擋在唯一出口。檢視模式攔在 save()，不靠隱藏按鈕
  5. 刪除要說實話。對話框講真正會發生的事，不講嚇人的空話

The Rule

主檔隨時可改。工單與工作量記錄是已經發生的事，抄了就凍結，一個例外都沒有。
建立工單是唯一一次讀款式。此後款式改名、改價、甚至被永久刪除， 工單與底下的記錄都不受影響。

這條規則禁止什麼

不可以為什麼
編輯款式時回頭改工單或記錄工單是談定的合約，款式只是模板
改客戶名稱時回寫 wo.custName同上。工單記的是當時的名字
員工改名時回寫記錄姓名一律走 empDisp(empId)，記錄不存名字
在工單上蓋「已請款」旗標查 invoices 就知道。旗標會有人忘記清
在記錄上存 price問工單。存了就會有一天兩邊不一樣
請款單品項存 styleId 再去查款式名請款單是寄出去的文件。款式改名會改到舊單，款式被刪還會讓品項名變空字串
請款單只存 senderProfileId同上。發件人改地址，所有舊單重印都變新地址；發件人被刪則抬頭整片空白

請款單也在「抄了就凍結」這一側

請款單跟工單、工作量記錄一樣，是已經發生的事。它身上有兩份快照：

快照抄的時機讀取
items[].name使用者打字當下，就是那串文字_invItemName(it)（name 優先、styleName 墊底）
sender存檔當下抄整份發件人invSenderOf(inv)（快照優先、主檔墊底）

senderProfileId 留著只是記「當初挑了誰」，列印不靠它。 _invSenderForSave() 只在換了發件人時才重抄——否則進去改個發票號碼再存， 快照就被刷成主檔現在的樣子，凍結等於白做。

唯一的例外

常用任務（employee.tasks）屬於主檔那一側， 對應的客戶／款式／工段被刪除時會自動清理（renderEmpBlock 裡）。 它不是「已發生的事」，所以不適用凍結規則。

歷史教訓

這套系統過去所有難查的 bug，都是同一種病：同一份資料存了兩次，其中一份忘了更新。 工段改編號沒同步到工單、刪薪資單時拿款式的價覆蓋記錄、款式改名後報表顯示舊名… 每一個都是。修法一律是「刪掉副本、改成推導」，不是「多加一條同步」。

03　資料模型

全部掛在頂層 let db = {...}。所有集合都是陣列，id 由 uid() 產生。

// 軟刪除：status 'active' | 'deleted'，不是真的移除
let db = {
  customers:      [],  // 客戶
  styles:         [],  // 款式（含工段 ops）
  employees:      [],  // 員工（含 tasks / tagIds / insurance）
  workOrders:     [],  // 工單（含工段快照 ops）
  records:        [],  // 工作量
  payrollEntries: [],  // 薪資單（＝結算鎖）
  mSalaryHistory: [],  // 月薪（生效月制）
  insurance:  {health:[], labor:[]},
  salaryRates:{snackRate:0, overtimeRate:0, bonusOptions:[]},
  tags:           [],
  machines:       [],  // [{id, name}] — 工段存的是 name 不是 id
  invoices:       [],  // 請款單
  senderProfiles: [],  // 請款單抬頭
  exportedAt:     ''   // 每次 save() 更新，供雲端比新舊
};

customers

{ id, code, country, name, phone, mobile, contact, taxId, address, createdAt, status }

code 是客戶代號 <國別><三位流水>（TW001）。 由 _custNextCode(country) 配發，配發後固定不變，刪掉的號不回收。

styles

{ id, custId, custName, name, photoIds:[], createdAt, status,
  ops:[ { id, code, name, machine, price, createdAt, status } ] }

唯一鍵是客戶＋名稱。ops[].price 是元／打，只當作開工單時的預設值。

workOrders

{ id, woNo, custId, custName, styleId, styleName,
  startDate, endDate, targetQty, note, manuallyDone, createdAt,
  ops:[ { opId, opCode, opName, machine,
          basePrice,   // 款式原價（建單當下的快照，不可改）
          adj,         // 補貼輸入字串 '+20%' / '-2' / ''
          adjNote,     // 補貼原因（純備註，已結算也可改）
          price,       // 最後單價 = basePrice ± adj，算工資用這個
          adhoc } ] }        // true = 臨時工段（款式沒有）

ops[].opId 沿用款式工段的 id；臨時工段自己 uid()。 woNo 由 _woNextNo(custId, startDate) 產生：<客戶代號>-<開工年>-<三位流水>。

records

{ id, date, empId, woId, opId, qty, createdAt }
只有七個欄位

客戶、款式、工段名稱與編號、單價、款式原價、員工姓名全部不存， 一律透過 推導層 回頭問工單與員工檔。 qty 的單位是件，不是打。

payrollEntries

{ id, empId, ym:'YYYY-MM', pieceWage, mSalary, snackAmt, overtimeAmt,
  productionBonusAmt, subsidy, allowance,
  healthInsAmt, laborInsAmt, laborRetirementAmt, incomeTaxAmt,
  agencyFee, examFee, boardFee, permitFee, otherDeductAmt,
  netPay, unlocked, createdAt, updatedAt }

這張表就是結算鎖。unlocked:true 代表正在解鎖調整中，此時不算鎖住。 mSalary 是結算當下的月薪快照，之後刪月薪紀錄也不影響。

invoices

{ id, invoiceNo, woId, date, dueDate,
  customerId, custName, custTaxId, contactName, contactPhone, contactMobile,
  items:[ { name, unitPrice, qty, note, locked? } ],
  taxed, receiptNo, senderProfileId,
  sender:{ name, companyName, address, phone, mobile, email,
           bankName, bankBranch, accountName, bankAccount },
  paid, createdAt }

woId 選填。有值＝從完工工單產生；空＝獨立開。一張工單最多一張請款單。

items[].unitPrice 是客戶售價，與工單的計件工資是兩回事，永遠手動輸入。

items[].name 是自由文字，不是款式參照——請款單要開的東西不一定是款式 （運費、樣品費、重工費）。4.0.1 之前的舊格式是 {styleId, styleName}， 相容路徑已隨遷移層一起拆除。

items[].locked 標記從工單帶進來的那一列：品項名與數量鎖住、不給刪，只有單價可填。 sender 是開單當下的發件人快照，見「02 架構核心」。

mSalaryHistory

{ id, empId, amount, effectiveFrom:'YYYY-MM', createdAt }

取用走 getMSalaryForMonth(empId, ym)：effectiveFrom <= ym 之中最新的一筆。

employees

{ id, name, empNo, createdAt, status,

04　推導層

記錄只有七個欄位，其餘全部從這一層取。不要繞過它直接讀 r.xxx。

函式回傳來源
recWo(r)所屬工單物件_woById(r.woId)
recWoOp(r)工單裡的那個工段wo.ops[opId]
recCustId(r)客戶 idwo.custId
recCustName(r)客戶名稱wo.custName
recStyleId(r)款式 idwo.styleId
recStyleName(r)款式名稱wo.styleName
recOpName(r)工段名稱wo.ops[].opName
opCodeOfRec(r)工段編號wo.ops[].opCode
opLabelFromRec(r)1. 車縫編號＋名稱
recPrice(r)最後單價wo.ops[].price
recBase(r)款式原價wo.ops[].basePrice
recWoNo(r)工單號wo.woNo
recEmpName(r)純姓名（匯出／排序用）employees[empId].name
recEmpDisp(r)含 #編號（畫面用）empDisp(empId)
recEmpName vs recEmpDisp

兩者不可混用。recEmpDisp 帶 #7 前綴，只給畫面； recEmpName 是純姓名，給 CSV 匯出、列印抬頭、排序與分組鍵。 混用會讓匯出的 CSV 出現「#7 王小明」。

沒有 fallback，推不出來就是壞了

function recCustName(r){ return recWo(r)?.custName || ''; }

4.0.1 之前這裡有一層 _pick(推導值, 記錄自己存的)，用來相容改版前那種 「記錄身上也存一份客戶／款式／單價」的舊資料。舊資料全部轉換完成之後整層拆掉了。

現在推不出來就是資料真的壞了，一律回空字串／0，不要拿別的東西頂替。可以這樣做的前提是兩個守門員：

  • 工單只要有記錄就刪不掉 → recWo(r) 不可能是 null
  • 工段只要有記錄就移不掉 → recWoOp(r) 不可能是 null
不要再加回 fallback

看到某筆記錄的客戶名是空的，正確的反應是去查為什麼工單不見了， 不是在這裡補一個 || r.custName。那樣只會把資料損壞蓋起來， 而記錄身上早就沒有 custName 這個欄位了。

工單索引

let _woIdx = null, _woIdxSrc = null, _woIdxLen = -1;
function _woById(id){
  const src = db.workOrders || [];
  // 陣列換身分或長度變了就重建 —— push / filter / 整包換掉 db 都涵蓋
  if(_woIdx === null || _woIdxSrc !== src || _woIdxLen !== src.length){
    _woIdxSrc = src; _woIdxLen = src.length;
    _woIdx = new Map(src.map(w => [w.id, w]));
  }
  return _woIdx.get(id) || null;
}

沒有這個索引的話，1,500 筆記錄 × 每欄一次線性 find 會很慢。

請款單的讀取器

同一套「快照優先、主檔墊底」，只是這裡凍結的是文件而不是記錄。

函式回傳順序
_invItemName(it)品項名it.name ?? it.styleName ?? ''
invSenderOf(inv)發件人資料inv.sender || 主檔 find || {}
_spSnapshot(s)做一份發件人快照明列十個欄位，主檔加欄位不會默默滲進來
_invSenderForSave(id, sid)存檔要寫的快照沒換發件人就沿用原本那份，換了才重抄
列印不要自己去 find 發件人

原本寫的是 db.senderProfiles.find(x => x.id === inv.senderProfileId) || {}， 發件人一被刪抬頭就整片空白，而且列印出來看不出少了什麼。一律走 invSenderOf()。

05　不變條件與守門員

推導成立的前提，以及維持它的那些擋門。改動時不要繞過。

前提

記錄靠 woId 找到工單，靠 opId 找到工段。這條鏈斷了，客戶／款式／工段／單價全部推不出來。

守門員擋什麼位置
工單底下有任何記錄就完全不給刪deleteWorkOrder()
工單工段已結算不可改價／移除；未結算但有記錄不可移除_woOpsRemove() / saveWorkOrder()
員工有記錄／薪資單／月薪／常用任務就不給永久刪hardDeleteEmployee()
工作量記錄已結算不可改、不可刪deleteRecord() / saveEditRec()
客戶・款式底下有工單就不給永久刪hardDeleteCustomer() / hardDeleteStyle()
客戶與款式其實不是推導的必要條件

實測把它們軟刪、硬刪，工單與記錄照樣顯示、照樣算工資、照樣列印，甚至還能繼續輸入工作量—— 因為工單自帶完整快照。守門員仍然擋著，但理由是別的： 那張工單將無法再編輯，而且記錄上不會再標示「(已刪除)」。 對話框寫的就是這個真實理由。

兩個「算出來的」狀態

// 結算鎖：該員工該月有未解鎖的薪資單 = 鎖住
function _isMonthLocked(empId, ym){
  const e = db.payrollEntries.find(e => e.empId===empId && e.ym===ym);
  return !!e && !e.unlocked;
}
function _isRecLocked(r){ return _isMonthLocked(r.empId, r.date.slice(0,7)); }

// 請款狀態：有沒有請款單指向這張工單
function woInvoice(woId){ return woId ? db.invoices.find(v => v.woId===woId) : null; }
function woInvoiced(woId){ return !!woInvoice(woId); }

兩者都不在被鎖的物件上存旗標。刪掉薪資單，那個月自動解鎖； 刪掉請款單，工單自動回到未請款。沒有人需要記得回頭清。

工段層級的鎖

let _woSettledByOp = {};  // opId → 已結算的記錄數
let _woRecsByOp    = {};  // opId → 記錄總數
function _woOpLocked(opId){  return (_woSettledByOp[opId]||0) > 0; }
function _woOpHasRecs(opId){ return (_woRecsByOp[opId]||0)    > 0; }

在 openWorkOrderModal() 裡重算。鎖是逐工段的——同一張工單可以一部分鎖住、一部分還能改。

手機檢視版

寬度 ≤ 820px 時整個換掉桌機版面（#m-app），四個分頁： 總覽 / 工單 / 款式 / 薪資。它只讀 db，不呼叫任何桌機 render，也永遠不會呼叫 save()。 所有函式以 m 開頭，狀態在 _mTab / _mDetail / _mQuery / _mYm / _mWoFilter。

月產出不能把記錄的 qty 相加

一件衣服經過十幾道工序，每道各一筆記錄。相加等於同一件算十幾次—— 實測 2026-07 相加是 53,250 件，真正完工只有 3,549 件。

正確做法是 _woDoneDate(wo)：逐筆推進各工段的累計， 第一次讓最小值追上 targetQty 的那一天就是達標日，用它歸月。 這跟 _woCalc().doneQty 取最小值是同一個道理——最小值才是真正走完全部工段的件數。 手動完工的工單沒有這種日期，退回 endDate；兩者都沒有就不計入。

反過來說，計件工資相加是對的：每一道工序的錢本來就都要付。 同一個畫面上兩格的口徑不同，是刻意的。

金額用手機專用的 m$() / mNum()（帶千分位）。 桌機的 fmt$ 不要改——CSV 匯出與列印模板都用它，塞逗號會讓 Excel 分欄跑掉。

照片 id 的格式

function _photoIdFor(styleId){ return `${styleId}--${uid()}`; }

用 -- 當分隔（styleId 本身含一個底線）。這樣不必下載圖檔就認得出哪張照片屬於哪個款式。單一款式上限 PHOTO_MAX = 3。

save() 與 load()

save() 是唯一的寫入出口：擋檢視模式 → 更新 exportedAt → 寫 IndexedDB → 排程雲端同步。

版本閘門（取代了遷移層）

4.0.1 之前有一個 _applyMigrations()，在載入／還原／雲端拉回三個地方 把舊結構補起來。舊資料轉換完成後整個拆掉了，改成把舊格式擋在門口。 

const DATA_VER = 9;
function _isSupportedData(data){ return Number(data?.version) >= DATA_VER; }
入口有沒有 version做什麼
importBackup()有低於 9 直接拒絕，訊息寫在還原區
GitHub 拉回有（{version:9, ...db}）低於 9 不套用，同步狀態顯示錯誤
load()（IndexedDB）沒有擋不了。save() 寫的是 db 本身，裡面沒有 version 欄位

IndexedDB 那條路靠 db = {...db, ...data} 兜底：缺少的頂層鍵會沿用 db 宣告時的預設值，所以結構不會缺。這是為什麼 db 的宣告要把每個集合都寫出來。

為什麼是擋下而不是照收

推導層的 fallback 已經拆了。舊備份照收的話，缺的集合會是 undefined（直接爆）， 而記錄的客戶與款式名會安安靜靜變成空白——後者比報錯難查得多。 寧可讓人看到一句「這是舊格式」，也不要收下一份看起來正常、實際上名字全掉光的資料。

07　金額與規則

計件工資

function calcSub(qty, price){ return Math.round(qty * price / 12 * 10) / 10; }
單位

qty 是件，price 是元／打，所以要 ÷12。四捨五入到小數一位。 工單的 targetQty 也是件，兩者可以直接比。

補貼解析

// 一律是「增減」，不是「設為」。回傳套用後的新單價，無法解析回傳 null
function _woParseAdj(raw, cur)   // '10' '+10' '-2' '20%' '-10%'

三層的關係：price = basePrice ± adj。_woOpBase(o) 在沒有 basePrice 的舊資料上退回 price（視為無補貼）。

兩層顯示

function _priceParts(r){
  const cur = recPrice(r), base = recBase(r);
  const diff = Math.round((cur - base) * 10) / 10;
  return diff===0 ? null : { base, diff };   // null = 沒補貼，只顯示一層
}

const {doneQty} = _woCalc(wo);

const isDone   = autoDone || !!wo.manuallyDone;

工作量表的欄位機制

_recAllCols() 是單一定義來源，同時決定 colgroup、表頭、排序與儲存格：

{ k, label,
  def,       // 還沒調過欄寬時的寬度（可用 %，空字串＝吃剩餘）
  fb,        // 需要 px 卻量不到時的後備值
  sort,      // 排序取值；沒有 sort 就是不能排
  cell,      // 產生儲存格

表格欄寬的通則

其他表格用 table-layout:fixed + <colgroup>。慣例是：

  • 內容長度固定的欄（日期、金額、狀態、功能鍵）給死寬度
  • 長度不定的文字欄不給寬度，平分剩餘空間
  • 不要只留一欄不給寬度——它會吃掉所有剩餘空間，寬螢幕下開一個大洞
  • 寬度要量不要猜。功能鍵欄要照最多按鈕的那一列算（有些列會多一顆完工切換）

11　已知陷阱

都是實際踩過的。

日期不要用 toISOString()

// ✗ UTC+8 會退回前一天
new Date().toISOString().slice(0,10)
// ✓
_ymd(new Date())

qty 是件不是打

calcSub 有 ÷12。任何顯示「N 打」的地方都是標錯了。

放寬限制時要回頭找誰依賴它

真實案例

「允許工單期間重疊」放寬之後，資料健康檢查的重複判定鍵 （empId|date|styleId|opId，少了 woId）就會把兩張不同工單的記錄判成重複， 而那個畫面上的「合併」「只保留這筆」會刪掉真實的工作量。 這類 bug 靜態掃描抓不到，只有讀 diff 時問「這條規則鬆了，誰本來靠它？」才會浮出來。

select 找不到 option 會靜默變成空字串

編輯既有工單時，如果客戶／款式已被刪除、不在下拉選單裡， sel.value = wo.styleId 會靜默設成 ''，接著必填檢查抱怨「請填寫所有必填欄位」—— 抱怨的是它自己弄丟的東西。編輯時要把當前值補進選單（標示「（已刪除）」）。

存檔不可以把凍結的名字洗成空白

// ✗ 主檔被刪除時 cust 是 undefined → 寫成空字串
custName: cust?.name || ''
// ✓ 退回工單自己凍結的那份
custName: cust?.name || wo.custName || ''

記錄的客戶／款式名是從工單推導的，一洗掉就是整批記錄同時變空白。

badge / class 要確認 CSS 真的存在

class="warn" 沒有對應規則（只有 .msg-warn），提示會變成沒有樣式的純文字。

全域 Enter 導航會點掉 modal 裡第一個 .btn-primary

真實案例

焦點在 modal 最後一個欄位時按 Enter，處理器會 modal.querySelector('button.btn-primary').click()。 在清單型 modal（「從工單建立請款單」）裡，第一個 .btn-primary 不是確認鈕， 是清單第一列的「建立」——等於在搜尋框按 Enter 就直接對最上面那張工單開了請款單。

清單型 modal 的所有輸入欄位都要標 data-modal-nav="skip"，而且 要全部標：只標一個的話，另一個就變成「最後一個」，照樣中招。

動態列不要拿 rows.length 當索引

// ✗ 刪掉中間某列之後，長度就跟最大索引對不起來
const i = tbody.rows.length;   // 3 列刪掉第 1 列 → i=2，做出第二個 inv-row-2

id 一重複，getElementById 只回傳第一個，之後讀寫默默跑到別列去，會存錯資料 （畫面上會先看到列號跳成 1,2,3,4,8）。新增與刪除都走「重讀全部 → 整份重畫」， 索引才會永遠是連續的 0..n-1。順帶好處：一列的長相只有一個地方定義， 不會出現「改了一份忘了另一份」。

切頁函式可能會覆蓋你剛設好的篩選

showPage('progress') 內部會呼叫 woClearFilters()，而那個是把日期 重設成預設區間不是清空。從請款單跳到來源工單時若先清篩選再切頁，會被蓋回去， 工單只要落在預設區間外就被篩掉，跳過去是一片空白。清篩選必須在切頁之後。

flex 子元素會把固定高度撐破

height:430px 配上 flex:1 等於沒寫——flex:1 會讓它跟著內容長。 拿掉之後仍不夠：align-items:stretch 只保證「至少跟最高的一樣高」， 內容更高時照樣撐長。要讓某一欄完全不參與高度計算，得 position:absolute;inset:0 包在 flex:1;min-height:0;position:relative 的框裡。

刪程式碼時用大括號配對算範圍

手寫行號或用空字串當結尾標記都出過事（多刪了下一個函式的開頭、或一次砍掉三千行）。 刪完一定要驗括號平衡，並重掃有沒有連鎖產生的新死碼。

12　常見改動

新增一個記錄欄位

先問：這個值能不能從工單或員工檔推導出來？能的話就不要存，加一個 recXxx()。

集中在「核心計算／規則」區段。_calcNetPay 是實發的唯一公式，三處呼叫共用，不要各自複製。

  1. 先在瀏覽器量出每一欄內容實際需要多寬（含表頭文字）
  2. 固定內容的欄給「內容 + padding」剛好
  3. 剩餘空間給長度不定的文字欄，可以多欄平分
  4. 檢查 min-width 別讓一般筆電寬度就開始橫捲

  • 十個頁面都能開、無 console 錯誤
  • 所有 onclick 都指得到函式

13　演進與已移除的功能

工單制重構（v3.5）

最大的一次改版。工作量記錄從自己抄一份客戶／款式／工段／單價， 改成只記 {id, date, empId, woId, opId, qty, createdAt}，其餘全部推導。 單筆 458 → 192 bytes。

遷移分四步，中間的驗收點是唯一的安全網：

  1. 建推導層，欄位先留著，把所有讀取點導過去
  2. 逐筆對照「記錄存的」與「推導出來的」，全綠才往下走
  3. 停止寫入，清掉既有記錄的繼承欄位
  4. 拆掉一次性的遷移工具
